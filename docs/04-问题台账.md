## #1 油耗数据冻结在最后一次（✅ v3 已修，勿回退）

**现象**（用户原话）
> 「测试结束，迪友油耗刷新正常且很及时，我们油耗数据获取失败，数据固定在了上一次的数据。」

**真根因（v3 实测定案）**

不是通道掉线，是**优先级写反了**：

```java
// 旧代码 pollStats() 里 Stat 排在第一位
double sFuel = Stat.fuel(ctx);
if (sFuel >= 0 || sElec >= 0) {
    fuelPHM = sFuel; ...
    return;                     // ← 直接返回，下面的迪友分支永远走不到
}
...
if (dyElec >= 0) { ... }        // 迪友被排在后面，形同虚设
```

`BYDAutoStatisticDevice.getLastFuelConPHMValue()` 返回的是**上一次行程结束时的值**，本身就不刷新。
它一旦可读，就把迪友顶掉，界面当然"冻结"。

**修复**（`VehicleData.pollStats()`）

```
优先级 1：dyElec/dyFuel（迪友卡片，几百 ms 就在变）
优先级 2：Stat.fuel()/elec()（还没抓到过迪友时替补）
优先级 3：winElec/winFuel（遥测库行驶窗口）
优先级 4：lifeE/lifeF（累计寄存器）
```

附带：迪友值落盘 `/sdcard/clusterlab_dy.txt`，`refresh()` 第一行 `loadDyCache()` 读回，
开机首帧就是上次的正确值，不会先闪一下迪加口径。

**验证**：`CLUSTERLAB: api e=12.9 f=1.4 t=5.1` ↔ 迪友卡片 12.9/1.4，`12.9/3.5+1.4=5.09` ✓

**别再试**
- 别把 `Stat` 放回第一优先级——它就是"上次行程值"，天生不刷新
- 别用 `uiautomator dump`——车机上被 OOM kill（rc=137）

## #1b `ENABLE` 迪友抓取的时效降级——不要加

v2 曾建议「`nowDy - dyAt > 12s` 就降级到统计设备」。**实测不需要**：
迪友本身刷新慢（同一句能耗会挂十几秒），加时效降级反而会让数值来回横跳。
用户的态度是「从迪友抓，固定住不要回落迪加」——**保持只升不降**。

## #2 为什么迪友（第三方）能读，我们读不到

**结论**（已确认，别再反复问）
- 迪友桌面 `com.dy.launcher` 是 BYD **预装且签了平台证书**的应用，`BYDAUTO_*` 权限是 `signature|privileged` 级，

## #3 开机"闪退一次"（✅ 已修，勿回退）

**现象**：「1.0 的时候都不会闪一下，为什么我们现在会开机闪一下？界面已经拉起来了，还要闪退一下」

**根因**：启动链有**两条路径撞车**——
1. `ActivityOptions.setLaunchDisplayId(1)` 在进程内抢先创窗（~20ms）
2. `BootReceiver` 等 Shizuku 就绪后又 `am start-activity --display 1` 一次

第二条让已有 Activity **重建**，用户看到的就是"闪一下 / 闪退一次"。

**修复**：只保留路径 2，且 `am start` 前先 `dumpsys` 查 display 1 上有没有我们的 `ActivityRecord`，
有就跳过。用户明确同意这个取舍（「不差那几毫秒」）。

**别再试**：任何"双保险"写法都会重现这个问题。

## #4 无障碍服务"僵尸绑定"

**现象**：油耗抓不到，但 `settings get secure enabled_accessibility_services` 里明明有我们。

**根因**：`settings` 里的列表 ≠ 系统真实绑定。force-stop / quickboot / 上电时序都可能让服务卡在 `Binding services`。

**处理**（`KeepAlive.healAccessibility()`）：
1. 不在列表 → 补进去（写两次，中间 sleep 1s）
2. 在列表但 `dumpsys accessibility` 的 Bound 段没有 `ClusterLab` → **温和重绑**：
   把本服务从列表摘掉 → sleep 2.5s → 写回 → sleep 2.5s

**绝不能做**：
- ❌ `force-stop` 自己 —— 界面消失 → assist 的 Watchdog 立刻拉起 → 又没绑上 → **杀-拉死循环**
- ❌ 反复 toggle `accessibility_enabled` 总开关 —— 会把迪友/迪加/迪+ 的服务一起解绑，它们重绑很慢

## #5 主线程阻塞导致无障碍绑定超时

**现象**：`CarAccess` 永远卡在 "Binding services"，日志一行都不出。

**根因**：本进程同时承载 `CardActivity`（绘制）、`KeepAlive`（tick 15s）、`CarAccess`（tick 400ms），
**都在主线程**。任一处在主线程做 `Shz.exec` / `Thread.sleep`，系统判定绑定超时。

**铁律**：主线程只做毫秒级操作。耗时任务一律 `new Thread(...).setDaemon(true).start()`。
`KeepAlive.tick` / `CarAccess.kickBaselineWorker` 都是这么写的，**别改回同步**。

## #7 歌词动画"一卡一卡往上走"

**根因**：滚出进度用**整行时长**做分母。长句（30s）时每帧位移 0.01px，量化到屏幕就是一格一格跳。

**修复**：改用固定时长窗口 `ROLL_MS = 420`——只在该行结束前 420ms 内匀速滚完。

**教训**：任何"跟时间线性插值"的动画，分母都不能是数据时长，必须是固定窗口。

## #8 超长歌词：截断还是换行（v3 定案：换行）

**v2 的做法（已废）**：当前行也强制单行 + `TruncateAt.END`，`curExtra` 恒 0。

**用户 v3 明确否决**：
> 「歌词太长会显示…，允许长歌词自动换行把上面一行挤掉，要把歌词完整显示完」

**v3 实现**

1. 所有行统一 `StaticLayout(maxLines=3)`，不再走 `drawSingleLine` 截断
2. 排版从"固定 `k × lineH`"改成**按实际盒高累加**：

```java
盒高 = 字号 + (行数-1) × INNER + GAPV     // INNER=34(句内) GAPV=18(句间)
当前行为锚点 → 先向下累加，放不下就停 → 剩余空间再向上填
```

3. 句内行距必须**小于**句间行距（用户原话）：
   - 句间 44px（`lcur + 18`）
   - 句内 34px（`setLineSpacing(2f, 1.05f)`）

**铁律**
- 不再用 `StaticLayout.getHeight()` 累加——它只含文字、不含行距，混用会让行距全乱
- 改 `setLineSpacing` 的 `2f` 时必须同步改 `INNER` 常量，否则排版错位

## #16 缓存槽位负数导致上方行不画（v3）

**现象**：`aboveLines` 加到 2~3 之后，「第一行看不见了」。

**根因**

```java
int slot = k + 1;                                   // k=-3 → slot=-2
if (slot < 0 || slot >= slCache.length) continue;   // 负数直接跳过
```

`aboveLines=1` 时 `k` 最小 `-1`（`slot=0`）勉强没暴露；加到 3 就露馅。

**修复**：`slot = k + 4`，`slCache/slKey/slText/slWidth/slSize` 数组 8 → 12。

## #17 CPU 占用过高（v3 已优化 36~42% → 11%）

**现象**：系统弹「CPU 占用过高」。

**四个热点与处理**

| # | 热点 | 证据 | 处理 |
|---|---|---|---|
| 1 | 歌词排版每帧拼缓存 key | `HeapTaskDaemon` 累计 **10.12s**（GC 压力） | 改用**引用+数值**比较，零分配 → GC **0.26s** |
| 2 | 绘制 tick 无条件 16ms | 60fps 常驻 | `lyricAnim ? 32 : 80`（只有歌词滚动/淡入时 30fps） |
| 3 | `ensureStatic()` 每帧重算 key | 十几个字符串拼接 | 150ms 节流 |
| 4 | 后台轮询过密 | `screencap` 每次合成 5.5MB | 导航 240→500ms；迪友 400→600ms；油耗 refresh 400→600ms |

**零分配写法**

```java
boolean stale = sl == null
        || slText[slot] != text                    // String 引用比较
        || slWidth[slot] != (int) maxW
        || Math.abs(slSize[slot] - size) > 0.5f;
```

**measured**：`top -p <pid>` 三次采样 10.7 / 11.5 / 11.5%（滚动瞬间 23%）。

**教训**：Android 自绘里**每帧字符串拼接**是隐形杀手，比绘制本身贵得多。缓存 key 一律用引用/数值比较。

## #20 静置一晚冷启动，油耗拿不到（🔴 → ✅ v4.0 已解决）

**现象**：车放一晚，第二天着车，仪表屏的油耗一直不刷新，停在昨天的数；有时显示 `--`。

**根因**：`VehicleData.pollStats` 优先级 1 是**迪友无障碍抓卡**（`CarAccess` 读「最近能耗」卡片文本）。
迪友自己也是冷启动，它的首页卡片要十几秒才渲染出能耗数据；这期间无障碍树里根本没有那两个节点，
抓到的永远是空 → 一直用 `/sdcard/clusterlab_dy.txt` 里的旧值（`dyStale` 只是个日志标记，不参与降级）。

**为什么"优先级 2 直读"救不了**：`Stat.fuel()` 反射 `BYDAutoStatisticDevice` 在普通 App 进程里
第一次就 `SecurityException`（signature 级），`Stat` 里一个 `denied` 标志位就永久停用了。

**解法（v4.0）**：把"读系统"这件事搬到有权限的进程里做。
用 ADB shell 权限起 `app_process` 常驻进程（d_service），在**系统上下文**里反射调 BYDAuto，
500ms 轮询后原子写到 `/sdcard/clusterlab_byd.txt`，主进程 `YBFeed` 直接读。
冷启动时 d_service 在 1 秒内就有值，不再依赖任何第三方 App 的渲染时机。

**教训**：数据源不能挂在"另一个 App 的 UI 树"上——它的生命周期和渲染时机都不归你管。

## #21 App 内自实现 ADB 授权（v4.0）

**目标**：不装 Shizuku，不连电脑，App 自己拿到 shell 权限。

**协议关键点（写错任一条都握不上手）**
1. 报文头 24 字节、**6 个 little-endian uint32**：`command, arg0, arg1, data_length, data_crc32(填 0 即可), magic = command ^ 0xFFFFFFFF`
2. `CNXN` 的 arg0 是 version `0x01000000`、arg1 是 maxdata，payload 必须是以 `\0` 结尾的 `"host::"`
3. `AUTH` 的 arg0：`1=TOKEN`（adbd 发）、`2=SIGNATURE`（你签）、`3=RSAPUBLICKEY`（你推公钥）
4. 签名算法是 **SHA1withRSA**（PKCS#1 v1.5），签的是 adbd 给的 20 字节 token
5. 公钥**不能**直接发 X.509/DER，必须是 adbd 认的旧结构：
   `struct { u32 len; u32 n0inv; u32 n[len]; u32 rr[len]; u32 exponent; }`，全小端，
   `len` = 模长的 32 位字数，`n0inv = -1/n[0] mod 2^32`，`rr = 2^(64*len) mod n`；
   base64 后拼 `" 名字"\0` 作为 `AUTH(RSAPUBLICKEY)` 的 payload
6. 一条连接上**只能串行**跑命令：并发 `OPEN` 会让 `WRTE/OKAY` 交错，输出串包

**现场确认**
```bash
adb shell getprop ro.adb.secure        # 0 → 免确认；1 → 首次会弹"允许USB调试"
adb shell getprop service.adb.tcp.port # 5555 说明 adbd 在 TCP 上监听
```
若 `ro.adb.secure=1` 且 adbd 只在 USB 上，需要先 `adb tcpip 5555`（一次性，重启可能失效）。

**坑**：`pkill -f d_service` 会把自己也匹配上（`sh -c` 的 cmdline 里就有这几个字），
必须写成 `pkill -f '[d]_service'`——方括号让正则不匹配自身。

## #22 仪表助理把迪加 / 迪友桌面的 adb 授权和无障碍顶掉（🔴 → ✅ v4.5）

**现象**：装了仪表助理后，迪加（com.van.diplus）和迪友桌面（com.dy.launcher）会掉 adb 授权、无障碍服务从列表里消失。

**根因**：见 03 迭代日志 v4.5 的三条 —— ① KeepAlive 每 20 秒 `settings put secure enabled_accessibility_services`（还会先摘掉自己再写回），与迪+方控抢同一个全局字符串，把我们读到的旧列表写回去就把别人顶掉；② 两个 App 各赖一条常驻 adb 连接 + 15 秒探活，占住 adbd 的待授权槽；③ `pkill -f '[d]_service'` 会杀迪友的常驻进程。

**结论 / 规矩**：

- 全局设置只读不写。要补自己的无障碍条目，只能「追加自己」，且限频（6 小时一次）。
- adb 连接用完即断，空闲 20 秒 reaper 兜底；exec 成功后退避归零，失败才指数增长。
- 杀进程只按自己的类名（com.byd.clusterlab.YBCore），进程名用 yb_core，不要占用别人的名字。
- 判断我们占了多少 adbd：`cat /proc/net/tcp /proc/net/tcp6 | awk '$3 ~ /15B3/ {print $8}' | sort | uniq -c`，uid 10083=clusterlab、10084=assist、10081=迪加、10179=迪友，2000=系统 shell。
## #23 开机不自启（🔴 → ✅ v4.6）

**现象**：测试反馈「我们的软件不会开机自启动了」。

**根因三条**：① v4.5 把 YBAdb 改按需连接后，connect() 只尝试一次，开机早期一次性失败就不再重试；② YBAdb.ping() 在主线程发起 socket 连接 → NetworkOnMainThreadException，退避还被推到 60 秒；③ 助理「停止卡片」用 am force-stop，包进入 stopped 态后系统不再投递 BOOT_COMPLETED，用过一次停止按钮就一直不开机自启。

**结论 / 规矩**：

- 开机链路必须「重试 + 有界」：connect() 后台线程每 3 秒重试、5 分钟封顶。
- 轮询方不许在主线程碰 socket；ping() 一律投到单线程池。
- 任何时候都不要对自己 am force-stop（含「停止」按钮），要停就发广播 + finish() + stopService()。

## #24 车机变卡：持续 screencap 是元凶（🔴 → ✅ v4.6）

**现象**：装了仪表助理后车机整体变卡。

**根因**：NavState 的导航探测线程每 120ms 调一次 NavProbe.sample()，每次 screencap -d 1 截整屏 5.5MB 写盘再删，等于持续写 IO + 每轮一次 adb 往返。按线程采样：该线程独占 7.6% 单核，主线程重绘 4.5%。

**改法**：高德广播有效期内完全跳过截图；兜底探测 5s/3s；静止画面不重绘；刷新节流全面放宽。实测 18% → 3%。

**排查手法**：/proc/<pid>/task/*/stat 的 14+15 字段做两次采样求差，按 comm 排名，一眼看出热点线程。
