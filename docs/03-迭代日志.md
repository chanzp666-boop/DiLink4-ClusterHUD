2. 「增加字体大小设置」→ 每元素独立 `size`（8~80 有各自上下限）
3. 「歌词也要有描边设置…全都是独立设置」→ 每元素独立 `stroke.on / stroke.w / stroke.night / stroke.light`
4. 「本次电耗/本次油耗/综合油耗不要放在数值里调颜色，单独拆开成一类标题」→ 去掉合并的 `num` 语义，改为 `cap` 标题 + `num` 数值 + `unit` 单位

8. 「所有的描边效果都是外部描边，颜色再多给几种深色」→ 描边线宽×2 + 24 色板每色 4 档
9. 「元素设置错乱了，设置项会互相影响」→ 修 `StyleEditor` 的 `syncing` 标志与 `refreshWeight()` 时序
10. 「透明度会影响粗细」→ 拆开 alpha 与 fakeBold 的绘制路径

### 音乐/歌词

### 一、油耗掉线（v1.1 遗留的 #1）

| 用户原话 | 排查结果 | 处理 |
|---|---|---|
| 「测试结束，迪友油耗刷新正常且很及时，我们油耗数据获取失败，数据固定在了上一次的数据」 | 走的是 `Stat` 直读分支，它在 `pollStats()` 里排在迪友**之前**，一旦能读就 `return`，迪友永远用不上；而 `getLastFuelConPHMValue()` 返回"上次行程"值，本身就不刷新 | 迪友提到**第一优先级**，`Stat` 降为替补；顺带把迪友值落盘 `/sdcard/clusterlab_dy.txt`，开机先读回 |
| 「油耗刷新要多久，我希望能实时」 | `refresh()` 节流 1500ms | 降到 400ms→最终 600ms（与迪友抓取周期对齐）；胎压单独节流 2s |

**结论**：`CLUSTERLAB: api e=12.9 f=1.4 t=5.1` 与迪友卡片 12.9/1.4 一致，计算 `12.9/3.5+1.4=5.09` 正确。

## v4.2（11-01 车机实测）

- **ADB 自授权打通（真正的坑在签名算法）**：adbd 不是对 20 字节 token 做 SHA-1 再签，
  而是把 token 当成「已算好的 SHA-1 摘要」，构造 3021 3009 0605 2b0e03021a 0500 0414 || token
  （35 字节）后做一次裸 RSA 私钥运算。用 Signature(SHA1withRSA) 会被判签名无效，
  adbd 于是不停发新 token——表现就是「点了允许还是过不去」。
  证据：从 Mac 的 adb 抓包，用模数做一次模幂，EM 尾部正好等于原始 token 而非其 SHA-1。
  改法：AdbCrypto.signToken 用 Cipher(RSA/ECB/PKCS1Padding) 直签 DigestInfo。
- **零弹窗**：AdbCrypto 支持导入主机密钥 /sdcard/clusterlab/adbkey.pk8（三行：
  PKCS8 base64 / 模数 n / 指数 e，解析用 new BigInteger(1, …)）。电脑上已被本车机
  授权的 ~/.android/adbkey 导进去即可免弹窗直连。
- 认证循环重写：第二次被拒才推公钥，之后每 5s poke 一次签名；探活不再抢锁
  （ops>0 跳过、连续 3 次才判失败），修掉「dumpsys 跑 8 秒把连接探活打死」的连环重连。
- **d_service 直读 BYDAuto 不成立**：uid 2000 也没有 BYDAUTO_*_GET

## v4.6（2026-11-02 00:05）开机自启修复 + 性能优化 + 权限精简

**触发**：测试反馈两条 —— ① 我们的软件不会开机自启动了；② 车机有点卡，要减少占用。外加用户要求：参考迪友/迪加怎么处理 adb 授权与无障碍兼容、删掉用不到的权限。

### 一、开机不自启的三条原因（全部修掉）

1. 🔴 **v4.5 把 YBAdb 改成按需连接后，connect() 只尝试一次**。开机早期 adbd/存储还没就绪，第一次失败就再也不重试 → 卡片永远不出现。现在 connect() 的后台线程会在 5 分钟内每 3 秒重试一次，成功即退出。
2. 🔴 **YBAdb.ping() 在主线程调 ensureOnce()**，触发 NetworkOnMainThreadException，还会把退避推到 60 秒。现在 ping 走单线程池执行，ensureOnce() 开头也调 permitMainNet()。实测：修前日志 `adb 启动 -> null`，修后 `adb 启动 -> Starting: Intent { cmp=com.byd.clusterlab/.CardActivity }`，3 秒内界面回来。
3. 🔴 **助理的「停止卡片」用的是 am force-stop**，这会把包装进 stopped 态，之后系统不再投递 BOOT_COMPLETED —— 用过一次停止按钮，下次开机就不自启了。现在改为广播 com.byd.clusterlab.STOP：BootReceiver 收到后 stopService(KeepAlive) + CardActivity.shutdown()（只 finish 界面）。实测停止后 dumpsys package 里仍是 stopped=false。

### 二、性能：18% → 3%

按线程采样定位到真凶：NavState 的导航探测线程每 120ms 调一次 NavProbe.sample()，而它每次都 scréencap -d 1 截整块仪表屏（1920x720x4 ≈ 5.5MB）写 /data/local/tmp，再 rm。等于持续 5.5MB/次的磁盘写入 + 每次一次 adb 往返。

改动：

1. NavState：高德广播 90 秒内有效时完全跳过截图；兜底探测降频到「未导航 5 秒一次 / 导航中 3 秒一次」（原来 120ms 一轮）。
2. NavProbe：不再每次 rm raw 文件（省一次 adb 往返 + 握手）。
3. CardActivity 的绘制节拍：静止画面完全不重绘（没有音乐、没有歌词动画时 1 秒才轮一次状态），有音乐 4fps，歌词滚动 25fps；LAYER_TYPE_HARDWARE 改 LAYER_TYPE_NONE。
4. VehicleData：刷新节流 600ms → 1500ms，胎压 2s → 5s，计数器 3s → 6s。
5. MediaListener：800ms → 1500ms。

**实测**：com.byd.clusterlab 单核占用 18% → 13%（降频截图后）→ 9%（静止不重绘后）→ 3%；assist 常态 0%。

### 三、权限精简

## v4.9.2 修「ADB 授权失效 / 界面起不来」

用户反馈：装 v4.9.1 后「adb 授权无效，软件无法启动」。抓下来是**两个互相独立的坑同时发生**，都已修并回归验证。

**坑 1：面板（clusterassist）的存储权限被 install -r 清掉了**
- 现场：`dumpsys package com.byd.clusterassist` → `READ_EXTERNAL_STORAGE: granted=false`。
- 后果：`AdbCrypto` 读 `/storage/emulated/0/clusterlab/adbkey.pk8` 报 `EACCES (Permission denied)` → `签名失败` → 面板永远 `adb=connecting`（界面显示「ADB shell 未就绪」）。面板的「启动卡片」走的是 adb，所以看起来整个软件「起不来」。
- 修：`YBPrivilege` 提权时顺手 `pm grant com.byd.clusterassist READ/WRITE_EXTERNAL_STORAGE`（主程序有 adb，循环自己闭合）。
- 回归：故意 `pm revoke` 两包权限 → 重启主程序 → 25 秒内 assist `granted=true` 且日志出现「握手成功 fp=d718f4021d9da9ec」。

**坑 2：自愈的存活判据看错了对象**
- 旧判据数 `dumpsys activity activities` 里 display 1 的 `ActivityRecord` 数量。实测：record 在（count=8/9），但窗口 `mViewVisibility=0x8`、`mDrawState=NO_SURFACE`、`isVisible=false`。
- 后果：自愈以为「卡片活着」，永远不再拉；仪表屏上却是空的。
- 修：判据改成问窗口管理器 —— `dumpsys window windows | awk '/Window #/ {w=$0} /isVisible=true/ && w ~ /clusterlab/ {c++} END{print c+0}'`（先验证过 `grep -A 24` 会截断、`-A 40` 会串到下一个窗口，所以用 awk 记当前窗口名）。
- 回归：`input --display 1 keyevent KEYCODE_HOME` 把卡片藏起来 → gate=0 → **6 秒后 gate=1**（KeepAlive 轮询 10s 内重新 `am start`）。

产物：apk/ClusterHUD-1.0-v4.9.apk（c220497542f39901…）、apk/ClusterAssist-1.0-v4.9.apk（f1bd25093a4df8e5…），版本号 v4.9.2，均已 install -r。

## v4.9.5 回滚 v4.10.1 + 真修「离开全屏导航再回来卡片不恢复」

v4.10.1 的方向（clear-task 反复重开）被现场否定：用户看到「一直在跳动左滑进界面」。
随即整段回滚到 v4.9.3 的 heal/BootReceiver（心跳短路、本地直拉分支都恢复原样），Ver 打到 v4.9.5，
只做一处针对性改动。

**三个真根因（都有日志/命令证据）**

1. 自愈把「心跳新鲜」当成「用户看得见」。被导航盖住时 CardActivity 的 View 照常 onDraw、
   心跳照常每 10 秒写文件，`if (beatAge() < 30000L) return;` 直接短路 —— 覆盖后永远不复查窗口。
2. **CHECK 判据一直是坏的**：字符串被写成 `awk '/Window #/ {w=$0}' '/isVisible=true/ ...'`，
   第二个引号段被 awk 当成文件名 → 每次执行都报
   `awk: can't open file /isVisible=true/ && w ~ /clusterlab/ {c++} END{print c+0}`，
   输出永远为空 → 判据恒为「不可见」。BootReceiver 里同一份字符串同样坏，一并修成单条 awk 程序。
3. 用 `am start-activity --display 1` 重建不可靠：我们的任务已经不在 display 1 上时，
   系统直接拒绝 —— `SecurityException: Permission Denial: starting Intent ... with launchDisplayId=1`
   （调用方 uid 2000）。任务还在 display 1 上时才放行（等于只是 resume）。

**改法**

- 判可见：单条 awk 问 `dumpsys window windows`，BootReceiver 同款。
- 心跳新鲜时也做一次轻量复查（20 秒最多一次），不可见才动手。
- 抬升方式改成搬任务栈：`am stack move-task <我们的 taskId> <压住我们的栈 id> true`。
  taskId 取 `am stack list | grep clusterlab | grep -o 'taskId=[0-9]*'`；
  栈 id 取 **display 1 顶层窗口**的 `mDisplayId=1 stackId=NN`（`dumpsys window windows` 里第一条）。
  不能用 mFocusedApp 里的 StackId：实测焦点在 carsettings 时它给 9，而真正压住我们的窗口在栈 21，搬进 9 无效。
  该命令要带 `2>/dev/null` 并把结果过滤成纯数字 —— `grep -m1` 提前关管道时 dumpsys 会把
  `Failed to write while dumping service window: Broken pipe` 混进输出。走 MOVE_TASKS、无动画。
  拿不到 id 时才退回 `am start-activity --display 1 --activity-no-animation`。
- 不设「谁盖住就不抢」的例外：第一版加了「焦点是导航 App 就跳过」，结果用户复现时焦点一直是 MeterActivity，卡片永远不回来。已删除该例外。
- 抬升后 30 秒内不重复，避免抖动。

**YBAdb 顺带修**

exec 之前不按流 id 过滤报文，别的流漏出来的 WRTE 会被拼进结果
（实测 TOP 这条命令收到过 `settings get secure enabled_accessibility_services` 的返回值）。
现在按 adb 协议的 arg1（对端的 remote id = 我们的 local id）过滤，只认自己这条流。

产物：apk/ClusterHUD-1.0-v4.9.5.apk（0cff1c6259618a6d…），已 install -r。

## v4.9.6 回滚「见缝就抢」，改成按仪表布局状态恢复

车主指正：v4.9.5 会在**任何**看不见的时候把卡片顶上来，结果仪表投屏盖到了别的软件上（不是地图）。
判据应该是车机的布局状态，不是我们自己的可见性。

**判据（车主给的）**：`getIntArray/getInt(1007, 1086337074)` 返回 **4 = 全屏布局**，这时才恢复界面。

**怎么读到这个值**（两条路，都有实测）

1. 本进程反射 `android.hardware.bydauto.instrument.BYDAutoInstrumentDevice.getInstance(ctx)`
   → `InvocationTargetException`（缺 BYDAUTO_INSTRUMENT 签名级权限），拿不到。
2. 退回迪加 Lua：`/api/sendCmd?cmd=lua:<base64>` 送
   `di.log('CLAY=' .. tostring(di.byd.getInt(1007, 1086337074)))`，
   再读 `/sdcard/vandiplus/logs/cmd.txt` 尾部取 `CLAY=` 的值 —— 实测返回 `ok=true v=4`。
   注意迪加的 Lua 沙箱**没有 io 库**（`attempt to index global 'io'`），所以只能借它自己的日志回传。

**改法**

- 新增 `src/clusterlab/src/com/byd/clusterlab/Layout.java`：`Layout.full(ctx)` 先反射、失败退迪加日志回传，读不到返回 -1（按「不是全屏布局」处理，宁可不动手）。
- `KeepAlive.heal()`：先取 `Layout.full()`，**不等于 4 直接返回**，什么都不做；
  等于 4 且窗口不可见时，才 `restore()`（`am stack move-task <我们的 task> <顶层窗口所在栈> true`，退回 `am start --activity-no-animation`）。
- 心跳过期（进程被杀/界面没了）那条原有自愈链路保留，同样先过布局门。
- 布局读取只在「卡片不可见」时发生（每次一条 Lua + 读日志尾），正常情况不产生额外开销。

产物：apk/ClusterHUD-1.0-v4.9.6.apk
